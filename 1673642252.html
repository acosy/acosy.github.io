Wasm Snapshots for Fast Startup

发表于 2026-05-05 分类于 技术 ， WebAssembly

下面是 2021 年 WebAssembly Summit 上关于 Wasm Fast Startup 的一个讲解视频，里面详细讲解了 Wizer 是怎么使冷启动更快的：

视频链接：Nick Fitzgerald — Hit the Ground Running: Wasm Snapshots for Fast Startup

以下为视频的 transcript。

Critical path to interactive:

Everything that happens before a program is interactive, is on our so-called critical path.

I’m using the umbrella term “interactive” to mean anything like handling events in a web application, or responding to an HTTP request in a web server.

So the platform needs to compile and instantiate your wasm module, and then your program’s one-time initialization code needs to run. And this is specific to each program. Finally, once all that has happened, your program is ready and interactive. On the web, we also need to account for sending wasm over the internet to the client.

1. Compilation

Compilation is generally the slowest part of this critical path. Wasm engines have gone to great lengths to reduce compilation related latency.

1.1. Tiered compilers

They use something called tiered compilation, where they start out by quickly compiling the wasm without any optimizations in a baseline compiler. This produces code pretty quickly, but it’s not very good code. It’s not very fast code.

You can start executing that code immediately, and then in a background thread, the engine is running the optimizing compiler. That’ll take longer because it runs more optimizations, but it produces better code. When that better code is ready, we actually dynamically switch execution from the baseline code to the optimized code.

There was a great talk at last year’s Wasm Summit about JavaScript core’s new wasm interpreter. So they actually have an interpreter in front of the baseline compiler, that’s then in front of the optimizing compiler.

1.2. Code caches

Another thing that engines use is code caching. So if the engine has already compiled this exact wasm binary to native code before, then it can reuse that earlier compilation result.

1.3. Ahead-of-time compiles

Even more aggressive is compiling the wasm to native code ahead of time. This is a technique that’s not available on the web, because a web browser doesn’t know ahead of time which wasm modules it’s going to have to see and have to run, but you can kind of think of code caching as an approximation to this.

Serverless environments, on the other hand, we can do ahead-of-time compilation there. So rather than deploy the original wasm program to the cloud, we can compile it to native code, and then deploy the native code to the cloud.

This completely removes compilation from the critical path. And remember, since compilation is the slowest link in that critical path, ahead-of-time compilation is a huge win here.

2. Instantiation

Instantiation is when a static wasm module, that kind of describes some state that it might have, is given imports and becomes a dynamic wasm instance with that state internally.

The big steps for instantiating wasm module are to allocate and initialize the modules, linear memories and tables.

Typically this is done with an on-demand approach, where you use mmap to reserve a bunch of space, potentially with some extra space at the end for guard pages so that loads and stores aren’t explicitly bounds checked. And then you iterate through each data segment and you copy the relevant data into memory at the specified offset. And similar things for elements, segments and tables.

But we can actually do even better than this if we know that we’re going to be instantiating many different wasm modules in a row. So wasmtime recently gained a pooling instance allocator that uses a newer feature of Linux kernel called userfaultfd.

With pooling allocation, instantiation basically becomes a no-op, because space is pre-allocated in the pool. So to allocate the space for the instance, we just pop off a free list. We don’t have to do any mmap or mprotect or any other syscall.

Memory initialization is literally a no-op, because we do it lazily. We wait until the wasm touches a page, which is going to trigger a page fault that we handle in user space via userfaultfd. And this fault handler is going to then copy that initialized data into the page before finally letting the wasm program continue.

I took a Markdown rendering program written in Rust, and I compiled it to wasm. I benchmarked how fast we can instantiate this wasm module in a loop on a single thread.

As you can see, the pooling allocator with userfaultfd is twice as fast and it takes less than 40 microseconds to instantiate each time.

This improvement is going to get even more pronounced in parallel contexts like serverless platforms, because every mmap or mprotect syscall is internally taking a virtual memory lock for the process inside the kernel. If you’re using on-demand allocation, this lock ends up highly contended, and this degrades both the amount the parallelism your system as a whole is getting, and also hurts individual instantiation times.

Instantiation in particular is really important because if we can get instantiation really fast, then we can have a new unit or new instance per unit of work. So for example, we can use a new instance for every HTTP request on a web server, and this gives you strong isolation guarantees. It means that bugs can’t persist across requests and take down other unrelated requests. It means that one malicious user can’t exploit a bug in a wasm program to manipulate another user’s request data. So this isolation property is hugely important.

3. Initialization

The final stepping stone on the critical path to interactive is any kind of program specific initialization. I’m talking about any kind of, like one-time set-up code that has to run before your program is interactive. Some programs might have a bunch of this initialization code while others might have none.

In contrast to compilation and instantiation, which are generally the wasm engine’s responsibility to make fast, making your own programs initialization code fast is your responsibility as a developer targeting wasm. One of the things you can do is you can make initialization happened lazily.

So if you’re working on, say, like a document editor and it needs a dictionary, you don’t need to build that dictionary until the user actually starts editing a document, rather than say, navigating the list of available documents that they could edit.

But even better than doing work lazily is having the work already done for you so you don’t need to do it now at all. So things like Rust’s build.rs files allow you to do arbitrary computation at build time and then kind of include serialization of the results in your final wasm binary.

And this is where my tool Wizer comes in.

3.1. Wizer

What Wizer will do is it will run the initialization code ahead-of-time, and it will save a snapshot of the initialized state as a new WebAssembly binary.

And now when you instantiate this new wasm binary, it’s already initialized. You don’t need to run that initialization code again.

Let’s look at a concrete example.

Here we have a spelling corrector. We give it my favorite typo that I make all the time whenever I write JavaScript, “funciton”. And the spelling corrector replies, “you know ‘funciton’ is misspelled, did you mean ‘function’?”

Yes, I did mean “function”.

So I’m using an off-the-shelf crate that influences functionality and is based on Peter Norvig’s classic tutorial on how to implement spelling correctors. What’s we’re looking at here is that the initialization routine.

What it does is it builds out lexicon that we use as a source of truth for determining whether something is a typo or not, and which word it might be a typo of.

First we create an empty lexicon object:

And then we open our dictionary file from the file system and each line of that file contains a different word in our dictionary:

And we read each word from the file and insert it into our lexicon:

And finally, we store the fully defined lexicon into a global variable so that we can use it later:

That’s the full initialization code.

This is our spelling corrector’s main function.

We have a build time configuration flag for whether we’re using Wizer or not. If we’re not using Wizer, then we need to call the initialization function from main ourselves. But if we are using Wizer, we know that it’s already been initialized, and we can kind of skip this step:

Whether or not we’re using Wizer, by the time we got here:

we know that the LEXICON global variable has been initialized, and so we can grab a reference to it.

And now we start iterating through the words given to us as command line arguments:

If the word is in our lexicon, then we know it must be spelled correctly, and so we can just ignore it.

However, for each of the misspelled words, we want to get a list of suggested corrections. If the suggestion list is empty, we just say that the word is misspelled, but if it’s not empty, then we take that first suggestion and we ask, “did you mean: blah?”

I measure the total time it takes to both instantiate the spelling corrector and getting a spelling suggestion for a “funciton” typo.

The Wizer version is 5 times faster because it’s not building a LEXICON at runtime or doing any kind of disk IO and reading the file. That’s already been done at pre-initialization time, and it’s readily available in wasm memory.

Let’s dig into Wizer’s execution model in a little more detail.

First by reviewing the lifetime of a wasm module without Wizer, and then next we’ll contrast this to the lifetime of a wasm module that does use Wizer.

So everything starts with the developer building the wasm binary from source. And then they deploy that wasm module. So this vertical line represents the point in time where the deploy happens. So everything on the right of this line up until “interactive”, that’s the critical path that we’ve been talking about. But everything on the left side of this line is not on the critical path. That’s just kind of developer time.

So for each user, wasm engine has to compile and instantiate the wasm program, and the program must initialize itself before it’s interactive. And again, some environments we can do ahead-of-time compilation, in which case we can ignore that compilation step. As we just saw, instantiation is fast, especially with pooling and userfaultfd, where it becomes nearly instantaneous, less than 40 microseconds in that original example. That means all that’s left on this critical path is the program specific initialization.

So with Wizer, we kind of lift that initialization and we put it on the other side of the deploy.

We do that initialization work once ahead of time before we ship the wasm binary to users, and then every user gets an already initialized wasm binary, and they don’t need to wait on initialization at all.

So if we’re also doing ahead-of-time compilation, and we have that fast instantiation, now we’re really hitting the ground running and we’re just getting to interactive pretty much instantaneously.

But what is Wizer actually doing inside that pre-initialization step, and what is involved in taking a snapshot of a wasm instance?

3.2. What State is in a Wasm Instance?

In order to take a snapshot, we need to know what state exists that we need to inspect and record and store in a snapshot.

3.2.1. Globals

So the first kind of state that exists in the wasm instance are globals.

These are single scalar values that are either constant or mutable. If they’re constant, we can kind of ignore them because they can’t change and so we don’t need to record them in our snapshot. But if they’re mutable, we do need to.

And each global is initialized with the constant expression. So in this case, it would be i32.const 1048576.

3.2.2. Linear memories

The second kind of state in a wasm instance are linear memories. These are what wasm is famous for. Everyone knows, you know, wasm has linear memory.

These are just huge arrays of bytes that are organized into chunks, called pages, of 64 kilobytes. Each memory has an optional, initial size, specified in number of pages.

In here, that’s 17. And also an optional max size, specified again in number of pages, 22.

Memories are all zero by default, but you can use data segments to initialize different regions of memory to arbitrary bytes. So each data segment specifies the offset within its linear memory to where it should splat the data and the data to be splatted, so in this case, it’s a "hello!".

3.2.3. Tables

There’re also tables inside wasm instances which are sort of similar to memories but for reference types like func ref or extern ref.

So elements segments are basically the same as data segments, but for tables. And so here f and g are the table elements that would be inserted into the table, and they would be functions defined elsewhere in the module.

We can actually ignore this for now because without bulk memory, tables are immutable after initialization and Wizer doesn’t support bulk memory yet. So we can just ignore it.

So that’s really all we need in the snapshot. It’s just memories and globals.

Those of you who are a little bit more familiar with the wasm spec might be asking, what about the wasm stack?

The stack is where wasm instructions operands come from and where its results go to. For example, the i32.add instruction is going to pop 2 i32 values from the stack. It’s going to add them together, and it’s going to push that sum back onto the stack.

We don’t need to worry about snapshotting stack because we only ever take snapshots when there are zero call frames active. Therefore, the stack is always empty.

This is great because generally engines don’t give us APIs for inspecting the stack because internally they’re using compilers that have an internal representation like SSA, and they’re doing transforms like dead code elimination to remove values that aren’t used, but technically would have appeared on the wasm stack so they would have to recreate the wasm stack.

For similar reasons we don’t need to snapshot the current program counter because there are not active function calls so there is no current program counter nor are there any return pointers or anything that we need to remember.

Finally you might be wondering what about implicit host state? What about the file system or environment variables, stuff that’s kind of ambient, not represented in the wasm instance, but is kind of around it and the wasm instance can interact with.

The answer is we ignore these as well. We don’t import during pre-initialization. The only way that wasm is kind of allowed to interact with the outside world is via imports, so we’re safe here.

For example, we don’t allow importing a memory because the wasm module might expect that the imported memory has environment variables already initialized at a certain offset. Wizer can’t know what it’s expecting or what it’s not expecting, so it wouldn’t know how to create a memory for this.

We do allow function imports, but what we do is we create dummy functions, that if you actually call them, they trap. And that makes the initialization fail. So if you don’t actually call in these functions and you successfully initialize your wasm module, then basically Wizer as a whole is completely transparent. And the resulting wasm module can’t tell whether initialization function was just called and so now it’s initialized, or whether it was pre-initialized with Wizer so there was no initialization function to call at all anymore. So it’s completely transparent.

The exception to all these is that you actually can opt into using WASI imports during initialization time. This allows you to do things like read files from the host file system during that kind of pre-initialization. This is what our spelling corrector did. But you need to realize that by the time main execution is running, maybe you’re on a completely different computer now, so with different file systems sitting underneath your wasm module. And a file you were just looking at, now it’s gone. Or you might not even have access to any file system anymore, like if you got deployed to the web.

So this is a bit funky, and kind of changes the execution model. You lose that transparency property that you otherwise would have had.

So we require explicitly opting into this functionality to kind of, say, “Yes I know what I’m getting myself into”, if you want to use web.

3.3. Wizer’s Phases

Now we know what we need to snapshot, let’s dive into Wizer’s implementation and figure out how it does the snapshotting.

There’re four main phases.

3.3.1. Instrument

The first phase is instrumentation.

The goal here is to take all that internal state and export it, so that later on in the snapshot phase, we can read that state out.

Here we have a module that defines both a memory and a global, and Wizer adds 2 new exports, __wizer_global_0 and __wizer_memory_0. If there was a second global, then there would also be __wizer_global_1 export, etc.

3.3.2. Initialize

The second phase is initialization. Wizer uses wasmtime to compile and instantiate the module. This is when we create any kind of dummy function imports that the module might require.

And then we run the initialization function. By default, this is the function exported under the name wizer.initialize, but you can configure it to be anything you want.

3.3.3. Snapshot

The snapshot phase reads all those exports that we inserted earlier in the instrumentation phase to create the snapshot structure.

The snapshot structure records what are the initialize values of each global, what are the new sizes of each memory after initialization, because they might’ve been grown during that initialization phase. And finally, which regions of memory have non-zero data. We record these as an offset into the memory, and then the raw Rust slice of that non-zero data.

And that’s it. So snapshots can contain a lot of data, particularly many data segments or large data segments, but there are not that many different kinds of data. So ultimately, Wizer’s implementation is really quite simple.

3.3.4. Rewrite

The final phase here is the rewrite phase, where we take the initial wasm, and we take that snapshot we just recorded, and rewrite the initial wasm such that when you instantiate it, you get something that’s already initialized and doesn’t need to run initialization code again.

Right off the bat, we can remove the start section, because if the wasm module had a start function, we already ran it. So we don’t want to run it again because that could actually introduce bugs.

And we update each memory’s minimum size to be the initialized size, because again it could have been grown during initialization:

And if that newly grown region has non-zero regions of memory, when we try to initialize those with data segments, if we didn’t grow it then we would have a bug.

Each global’s initialization expression is replaced with the associated value from the snapshot

And then we remove all of the original data segments because we’re going to create a whole new batch from each region of non-zero memory that we got from the snapshot.

That’s it. That’s the whole rewrite phase.

One final thing to notice about the rewrite phase, and kind of Wizer in general, is that we’re never mutating the code section. So dwarf debug info, which contains hard-coded offsets into the code section, it doesn’t get invalidated or it doesn’t break. This means that it’s just as easy to debug a wizened module as it is to debug the original unwizened module, which is a very nice property to have.

4. Space-Time Trade Off?

You might be thinking, isn’t this kind of just a classic space time trade-off? Because instead of doing this initialization computation at runtime, we’re doing it ahead of time, and then attaching the results to the wasm binary’s data segments, and these data segments can bloat the resulting wasm binary.

And it’s true. The spelling corrector example from earlier, it grew by a factor of 10, from 300 kilobytes to 3 megabytes after wizening. But also keep in mind that it’s encoding a dictionary into a queryable data structure in memory. And without wizening, we would also need to ship this dictionary file alongside the wasm binary so it could be read during main executions.

But it’s true that this extra space can hurt startup times in the web where we’re actually sending the wasm over the network. And this extra network transfer time might dwarf the time saved by being pre-initialized.

And so my advice would be that if you’re targeting the web, you should be aware of this and should keep your eye on the wasm’s file size and try Wizer out and see if it helps. It’s easy to try out. If it does help, then you just got something for free. If it doesn’t, well, it didn’t cost you anything anyways.

So it’s kind of true in this context, we do have a classic space time trade-off. However when it comes to memory usage, things get a little bit more subtle, because remember wasmtime’s pooling and userfaultfd instance allocation doesn’t actually initialize memory pages until they’re touched. So that means that data segments that are used during initialization that won’t ever be used again during main execution. They only take up virtual address space, which is really plentiful. And they are never committed or require backing by physical memory.

So in this context, actually there is no space time trade-off. It’s just purely a win-win.

Additionally, you can run a binary wasm-opt tool over the module after Wizer is done pre-initializing it. And this can actually remove functions that were only used during initialization and will never be used during main execution so they’re dead code. So you can actually shave off some code size this way as well.

5. Sneak Peek - JavaScript on Wasm

There was some programs that weren’t previously viable because their startup time was simply too slow, and you wouldn’t really even consider doing things that way. But Wizer unlocks these new possibilities. So I want to give you a sneak peek at something that we’re kind of investigating at Fastly.

What we’ve done is we’ve compiled the JavaScript engine to wasm and we’re experimenting with using Wizer to make it start up super fast.

Starting up a JavaScript engine can be slow, so it’s an obvious target for wizening, but we can actually do even better than that because after the JavaScript engine is initialized, there’s still a bunch more things that need to happen before the engine is ready to run, a particular JavaScript program. For example, the JavaScript source code needs to be parsed. And then it needs to be translated into the engine’s internal bytecode format. And the top of the script needs to be evaluated so that any event listeners are added and JavaScript global variables are initialized.

We can actually do all of this stuff during Wizer’s pre-initialization time. We can even grab a reference to the JavaScript main function so we don’t have to do a global property lookup on the critical path during main execution. Main execution just calls the saved main JavaScript function.

I benchmarked another Markdown rendering program, but this time it’s a Markdown renderer written in JavaScript, inside the JavaScript engine that we’ve then compiled to WebAssembly.

It takes about 25ms just to start up the JavaScript engine, and then another 5ms to parse this JavaScript bytecode and evaluate that top level. And that 5ms is specific to this relatively small JavaScript Markdown program. Larger JavaScript programs will take even longer to do these things.

But because we can do all that stuff during pre-initialization, none of this stuff needs to happen at runtime. So we’re about 6 times faster with Wizer.

Now maybe JavaScript isn’t your favorite language. The same pre-initialization with Wizer approach will work just as well with Python or Ruby or Lua, etc. There’s nothing special about JavaScript here.

So I think this is really cool, and it shows off how Wizer opens up new possibilities to us that weren’t viable before.
